## Run 4 — THE CASE BLOCK 22 ACTUALLY EXISTS FOR. Not asked for; run anyway.

**0/1/0 never puts a patient at two clinics.** It proves the mechanism and it
leaves the headline output of STEP 3 — `patients_at_both_clinics` — at zero
throughout, which means the column BLOCK 22 tells the owner to write down had
never once been observed non-zero. That is not evidence.

So one appointment was repointed to the tenant's **other** location, which is
exactly the state a Castelo Branco import leaves behind for a person Linda-a-Velha
already imported: appointments at a clinic, no membership of it.

```
update appointments a
   set location_id = (select l.id from locations l
                       where l.tenant_id='3a2d0711-…' and l.id <> a.location_id limit 1)
 where a.tenant_id = '3a2d0711-…'
   and a.id = (select id from appointments where tenant_id='3a2d0711-…' order by id limit 1);

```

**READ `1000 → 1001`, NOT `1000 → 1000`.** The patient gained a **second**
membership; the first was not replaced, moved or overwritten. That is the whole
behaviour BLOCK 22 is for, and a backfill that re-pointed the existing link
instead would have produced an identical `rows_to_insert` and a silently wrong
database.

**`patients_at_both_clinics` moved 0 → 1**, so the number `PROD-RUN.md` §5.1
tells the owner to write down is a number that works.

## What this proves, and what it does not

**PROVES:**

- The backfill finds nothing to do after a clean import (`0`), repairs a real
  gap (`1`), and is re-runnable (`0`).
- `INSERT <n>` equals STEP 1's `rows_to_insert` exactly, which is the check the
  runbook asks the owner to make.
- A patient at two clinics gains a **second** link, `1000 → 1001`, and
  `patients_at_both_clinics` reports it.
- Soft-deleted patients are excluded, and the exclusion prints its own count.
- Nothing in PR #1064 disturbed the import: every §6 and §7.1 count is identical
  to 2026-08-27c.

**DOES NOT PROVE, and it is the same limit every rehearsal has had:**

- **Two real deliveries.** The two-clinic case was produced by repointing one
  appointment, not by importing a second `pacientes.csv`. What the shared
  `id_paciente` path does to the ledger is reasoned from
  `packages/db/src/migration/upsert.ts` and the ledger's unique key, and
  measured in advance by BLOCK 13 — it has never been executed end to end.
- **Scale.** 1,001 links, not the 8,000–10,000 the delivery will carry. The
  statement is one `INSERT ... SELECT`, so it does not batch and does not
  degrade the way the row-by-row paths do, but that is an argument rather than a
  measurement.
- **Production's `patients.primary_location_id`.** Untouched here and untouched
  by the file. Its backfill is a separate, still-unbuilt item.
