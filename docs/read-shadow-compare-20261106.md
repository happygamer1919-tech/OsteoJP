## Known limits

- #1691's known limits stand unchanged (the two clocks, #1678's gap for `rescheduleOwn` and the importer, verdict 15's control, RK's unknown-free trail, R34 rehearsed on seeded rows only).
- **LATE-PASS rests on the run time.** The ULID's meaning is NOT VERIFIED; a late pass whose run was also created late decodes as on time and is NOT a LATE-PASS here (verdict 3 FAILs). LATE-PASS does not cover a late 21:45 pass that lands after 21:45 (#1720's "outside" arm): such a day FAILs and strategy reads it.
- **HARD-DELETE ties a mark to the first pass that had it due.** A hard-deleted visit's other predicates at that pass (status, a scheduling save, created before its mark) cannot be read once its row is gone; a mark the first pass did not take is tied to a whole heartbeat (printed), and the pass that really took it then reads short with nothing tied, so verdict 8 FAILs. The start is the start AT THE DELETE: a visit moved after its pass and before its delete is placed at the wrong mark, and verdict 8 FAILs (the safe direction). A visit whose `starts_at` changed with no audit row is placed by the delete's start alone.
- **LR reads recorded rows only.** A status changed by a writer that writes no audit row, or a booking row with no `status`, leaves the estado not established, and the mark is not LR (the safe direction). The request gate reads `origin` from the row now; no writer changes it after the insert. LR cannot show WHY the run did not wake (Inngest's record is not in the database); it says only that a run was planned and left nothing.
- **LR's condition 4 is built as "the last save that sends `appointment/scheduled` at or before the mark exists"** (strategy's acceptance, after the R4 review). It cannot see a sender that writes no audit row (the owner-run re-arm scripts), and it reads a request as a request by `origin` alone, as the dispatcher does (`is_unconfirmed_pedido`'s notification half cannot be read here); a move of a request whose estado at the move no row establishes does not count. The planning save must have planned the run for the mark's start (round 2). **A start change no audit row records is NOT in the safe direction on its own** (this line said it was until round 3, and that was wrong): a portal move (`rescheduleOwn`) or an importer write before a sending status save makes the start the read takes for that save stale, and a second one after it can bring the visit back to that stale start, so the read would see a run planned for the mark's start when the run was planned for another (a false LR). Only the case where the recorded starts never reach the mark's start was safe (not LR). Rule 1 is what makes the whole class safe: a portal move with a staff notification at or before the mark (1a), any window after the planning save in which the patient could have moved it (1b, which covers a portal move whose notification is missing), and any visit the importer wrote (1c) each fail condition 4. A recorded move away and back between the planning save and the mark fails it even when the original run may still be good (conservative by design).
- **A recorded sending save whose event was never sent.** `enqueueRemindersAfterCommit` logs and swallows a failed enqueue (`apps/web/lib/scheduling/reminders.ts:150` to `156`); the audit row stands. "Planned" is then not provable from rows: the read takes that save as the planner although it planned nothing. DIRECTION: it can only make a mark look planned that was not (a false LR), never the reverse; an earlier sending save's run, not cancelled by the missing event, may still stand for the same start, which is not a false accept. Under rule 1b no mark reads LR, so this cannot reach a printed LR row in this read; it is disclosed for the day the portal move records itself.
- **Owner-run senders the pins cannot see.** `packages/db/scripts/inc-1007-rearm-reminders-emit.mjs`, `obs-05-backfill-emit.mjs`, and on origin/main `r36-fallback-rearm-emit.mjs` (which runs inc-1007's `run()`) send `appointment/scheduled` without writing an audit row; the test pins the event's references to the two in this tree, but their sends are not rows. DIRECTION, mostly the safe one: a run they planned is invisible, so a planned mark can read "no save that sends" or a stale planned start, and stays UNEXPLAINED (verdict 13 FAILs). They can make an unplanned mark look planned only through their `cancelOn`: their event ends the sleeping run a recorded save planned, and the planner re-plans only the marks still ahead of its own clock (`computeDueReminders`, `functions.ts:153` to `161`, after a 2 second debounce) for the start the script read, so an event landing just before a mark ends that mark's run and plans none, while the recorded save still reads as its planner (a false LR, the same race S8 names for recorded saves). inc-1007 and r36 refuse any row whose mark falls inside their margin (30 seconds plus the sends plus 60 seconds, `markTooClose`); obs-05 has no such margin, so for it this race is not excluded. Under rule 1b no mark reads LR in this read.
- **LR does not read the dispatch's later gates** (the routing guard, the tenant's and the patient's channel switches, the contact): a run refused there would leave a claim and a ledger row (condition 1), so a mark that has neither is not one of them.
