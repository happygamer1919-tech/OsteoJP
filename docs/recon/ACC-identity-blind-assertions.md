# ACC-identity-blind-assertions — the triage, corrected against `main`

**Written 2026-08-19, re-derived from `origin/main` at `f23a110`.** Every claim
below was read out of the files it names in this session. Where it contradicts
the board card's own notes, the file wins and the contradiction is stated rather
than reconciled away.

---

## 1. What the card asked, and what it had already established

The card (`ACC-identity-blind-assertions`) swept `apps/web/e2e` on 2026-08-12
after PG8's Direction A passed for the wrong reason. It counted 170
`toHaveCount(N)` assertions and partitioned them: 66 identity- or run-scoped, 63
absence assertions (`toHaveCount(0)`), and **41 presence counts on a non-identity
locator** as the nominal at-risk set. It then argued — correctly — that the 41 is
an upper bound dominated by static UI structure, and named **three genuine
candidates**. It fixed none, on the stated grounds that none carries a gate row.

Its closing rule is the part worth keeping:

> When writing an assertion against the shared seeded database, ask: could a row
> this test did not create satisfy it? If yes, add identity.

**This document does three things.** It re-derives the three named candidates and
finds that none of them is a case. It reports one real case the sweep did not
name. And it states the limitation of the sweep's population, which is the
finding with the longest reach.

## 2. The three named candidates, re-derived. None is a case.

### 2.1 `notes-unification.spec.ts:111` — the card's "CLEAREST CASE FOUND". Not a case.

The card describes it as "an appointment dropdown for a **shared patient**;
another spec booking for that patient adds an option and the count moves."

**The patient is not shared. It is created fresh, per run, under a random name.**
`notes-unification.spec.ts:79-81`:

```ts
const name = `DuasModes ${uniq()}`;
const id = await createPatient(page, { fullName: name });
```

where `uniq()` is `Math.random().toString(36).slice(2, 8)`. And the dropdown is
patient-scoped by construction: `components/appointment-selector.tsx:41` loads
its options with `listPatientAppointmentsForNoteAction(patientId)` — that
patient's appointments and no others.

**No other spec can add an option to it, because no other spec can name the
patient.** `toHaveCount(2)` is one patient-level option plus the one appointment
this test booked, both run-scoped. Safe by construction.

### 2.2 `scheduling.spec.ts:277` — not a case.

`triggers` is `dialog.getByRole("button", { name: "Data da marcação" })` — date
pickers **inside the open batch-booking dialog**, one per row, generated by the
`2` this same test typed into `Nº de marcações` eleven lines earlier
(`scheduling.spec.ts:267-270`). The population is UI rows the test itself just
created inside a modal it owns. No database row can add one.

### 2.3 `camera-to-ficha.spec.ts:128-158` — not a case.

`cameraButtons` is scoped to `camera`, which is
`page.getByRole("group", { name: "Câmara" })` — a control group inside a panel
this test opened. The counts (2 → 3 → 2) track the camera's own phase machine.
Nothing outside the test can add a button to a group in its own page.

**All three are false. The card's caution — "the honest number is smaller than
the alarming one" — was right, and it was still not conservative enough.**

## 3. One real case, which the sweep did not name

`apps/web/e2e/therapist-blocks.spec.ts:260-261`, before this change:

```ts
const list = modal.getByTestId("blocks-list");
await expect(list.getByText("Bloqueio pontual")).toHaveCount(1);
await expect(list.getByText("Ausência prolongada")).toHaveCount(1);
```

Three facts, each read from the file named:

1. **The list is unfiltered.** `app/admin/working-hours/TherapistBlocks.tsx:177`
   renders `<ul data-testid="blocks-list">` and maps over `blocks` **whole** —
   every block that therapist has, with no date predicate. The population being
   counted is not "the blocks this test made".
2. **The therapist is a shared fixture.** Both this spec and
   `agenda-blocked-time.spec.ts` operate on `THERAPIST_NAME` from `fixtures.ts`,
   and `agenda-blocked-time.spec.ts:67-81` creates its own **`Bloqueio pontual`**
   for that same therapist.
3. **Both specs clear the whole list.** `agenda-blocked-time.spec.ts:52-65`'s
   `clearBlocks()` deletes **every** block the therapist has, in `beforeEach`
   *and* `afterEach` — not only the ones its own spec created.
   `therapist-blocks.spec.ts` has a `clearBlocks()` of its own doing the same.

So the assertion counts a globally-mutable list, keyed only by a badge label that
**every block of that mode shares**. There is no identity in it at all.

### Why this matters even though an exact count usually fails loudly

This deserves stating precisely, because the obvious objection is sound as far as
it goes. A contaminated `toHaveCount(1)` normally becomes 2 and the test goes
**red** — loud, harmless, and self-correcting. That is the ordinary case.

**The case that is not harmless is the compensating error.** If this spec's own
pontual save silently failed *while* a foreign pontual block was present, the
count is still 1, the assertion passes, and the spec reports as created a block
it never created. That is the card's own distinction, exactly:

> A skippable suite FAILS TO PROVE. An identity-blind assertion PROVES SOMETHING
> FALSE.

It has not fired because `playwright.config.ts` sets `workers: 1` and
`fullyParallel: false`, so the two specs never interleave within a run. **That is
a scheduling accident, not a property.** The assertion's correctness currently
depends on file ordering under a serial runner, and nothing states that
dependency anywhere.

### The fix

Identify each row by its **own run-scoped date** — `RUN_DAY_BASE` is
`60 + (Date.now() % 300)`, randomised per run, so a leftover row from an earlier
run lands on a different day — then assert the badge **inside** that row:

```ts
const pontualRow = list.locator("li").filter({ hasText: ptDate(date) });
await expect(pontualRow).toHaveCount(1);
await expect(pontualRow).toContainText("Bloqueio pontual");
```

Both halves are needed and they prove different things: **the row proves the
block is ours; the badge proves it is the mode we asked for.** The old assertion
collapsed those two questions into one count and could answer neither.

Pinned by `apps/web/lib/e2e-hygiene/identity-blind-assertions.test.ts`, including
a negative control that the forbidden pattern really does match the old line —
without it, a typo in the regex would make the guard pass for the wrong reason
and go on passing.

## 4. The limitation of the sweep's population, which is the longest-reaching finding

**`toHaveCount` was swept because it is greppable, not because it is where the
risk concentrates.** An exact count is the population that *self-corrects*: a
foreign row usually pushes it off the expected number and it fails.

The population that can pass falsely **as its ordinary behaviour**, not as a
compensating error, is the one nobody has swept: **visibility and text assertions
on a non-identity locator.**

```ts
await expect(page.getByText("Bloqueio pontual")).toBeVisible();   // any row will do
await expect(list).toContainText("Confirmada");                    // whose appointment?
```

These pass on **any** matching row — yours, another spec's, or the seed's — and
they fail only when *nothing* matches. Contamination makes them *more* likely to
pass, not less. That is the opposite of the direction the card's absence-assertion
argument relies on, and it is why the absence-versus-presence distinction the
card drew for counts does not transfer to this population unchanged.

**This is not swept and is not fixed here**, deliberately: it is a different and
much larger population, and estimating its size without doing the work would be
the alarming-number mistake the card explicitly refused to make. It is carded as
`ACC-visibility-assertions-unswept`.

## 5. What was NOT changed, and why

- **The DB-gated suites.** The card's finding stands and was not re-derived in
  full: 45 of 53 build fixtures with `randomUUID()` per run, and the 8 that do
  not assert about a shared artefact *on purpose* (the journal, the migration
  set, a seeded template, an ownership catalog). Their subject **is** the shared
  thing, so naming it is correct.
- **The 41-item nominal at-risk set**, beyond the three re-derived above. Reading
  the full presence-count list from `main` (55 matches on `toHaveCount([1-9])`
  today, across 15 files) shows it is dominated by two safe shapes: `<option>`
  counts carrying `hasText` with a **named** catalog entry — where the name *is*
  the identity and a count of 1 is a uniqueness assertion — and SVG chart
  structure (`data-marker`, `data-legend-type`, `data-marker-shape`). Neither can
  be satisfied by a data row.
- **A repo-wide baseline lock on presence counts** was considered and rejected.
  It would put maintenance friction on 55 assertions across 15 files in order to
  guard the population that already fails loudly, while leaving the population
  identified in §4 unguarded. Poorly targeted protection is worse than none,
  because it reads as coverage.
